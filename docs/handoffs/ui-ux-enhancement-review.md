# UI/UX 후속 기능 고도화 검토 및 핸드오프

검토 기준: 2026-10-07의 현재 작업 디렉터리. 다음 에이전트는 코드와 `AGENTS.md`를
다시 읽고 근거를 확인한다. 이 문서는 검토 근거·구현 계약·인계 맥락이며, 남은 작업의
우선순위와 완료 상태는 **`ROADMAP.md`에서만** 관리한다.

## 인계할 현재 상태

Body Frame은 한 사람이 체형 사진 변화를 기록하는 Android/iOS 오프라인 앱이다.
촬영이 루트이며 정면→좌측면→우측면→후면을 이어 촬영하고 리뷰에서 일괄 저장한다.
갤러리 등록, 기록 타임라인·방향 모아보기, 상세 수정, 비교 3가지 모드 및 저장·공유는
이미 구현되어 있다. 해당 기능을 새로 만드는 작업으로 오해하지 않는다.

직전 변경은 앱 내부 리브랜딩이다. 이름·심벌과 촬영 중심 동선을 유지하며
“같은 프레임, 쌓이는 변화”, 그린·뉴트럴 공통 테마, 기록 요약·촬영 진입점,
비교 단계 안내, 날짜 선택 상태, 큰 글꼴 대응과 원본 비율 표시를 반영했다.
`docs/brand-design.md`와 `docs/ui/`에서 방향과 실제 위젯 미리보기를 확인한다.
앱 아이콘·시작 화면은 아직 교체하지 않았다.

직전 검증은 `flutter analyze` 오류 없음, `flutter test` **256개 통과**다.
이번 검토는 코드 읽기 중심이며, 아래 위험을 실기기에서 재현한 결과는 아니다.
문서 작성만으로 테스트를 다시 실행했다고 보고하지 않는다.

인계 시점에 위 UI 변경은 **미커밋 상태**다. 변경된 `lib/`, `test/`와 새 브랜드 문서,
이미지, 이 핸드오프 및 ROADMAP 변경을 모두 보존한다. `git status --short`로 먼저
확인하며, 변경을 초기화하거나 이전 UI로 되돌리지 않는다. 다른 워크트리에서 시작하면
커밋 또는 검토 가능한 패치로 이 전체 기준 상태를 먼저 옮겨야 한다.

## 검토 결론

다음 구현은 신규 메뉴보다 **저장 안정성→비교 기준 일관성→설정 저장 신뢰성** 순서가
적절하다. 검색·다중 사진 선택은 장기 사용에 유용하지만, 먼저 원본과 사용자 선택이
안전하게 보존되어야 한다. BF-01~04를 다음 에이전트의 기본 범위로 권장한다.
BF-05~08은 범위에 자동 포함하지 않는다.

## 코드 근거와 구현 계약

### BF-01: 저장 중 변경과 재진입

**확인된 코드 구조, 실제 타이밍 문제는 재현 필요.**

- `lib/features/capture/capture_review_screen.dart`: `_save`는 비동기 원본 복사와
  DB 저장을 수행하지만 `_buildBody`의 재촬영·날짜·입력은 활성 상태다. `_retake`는
  임시 사진을 삭제하고 리뷰를 닫는다. 저장이 같은 파일을 읽는 도중 실행되면 원본
  준비 실패와 저장 흐름 충돌이 가능하다. 저장 버튼·PopScope만으로는 충분하지 않다.
- `lib/features/capture/gallery_import_screen.dart`: `_saveAll`은 변경 가능한
  `_items`를 await가 있는 루프에서 읽는다. 항목 제거·추가, 방향·날짜·메모 변경은
  저장 상태와 연동되지 않는다. 컬렉션 변경, 저장 내용 불일치, 완료 시 `_items.clear()`로
  새 선택이 사라지는 위험을 Fake로 재현한다.

계약: 저장 시작에 파일 경로·방향·날짜·라벨·메모·격자 값을 스냅샷으로 고정한다.
작업 중 입력·재촬영·목록 변경·중복 저장·화면 이탈을 일관되게 제어한다. 단순히
위젯만 비활성화하지 말고 핸들러에도 중복 실행 방어를 둔다. 실패 시 입력과 임시 원본을
보존하고 재시도할 수 있어야 한다. 기존 staging→rename, transaction과 rollback을
그대로 활용한다. 프로세스 종료까지 복원하는 영속 초안 기능은 이번 범위가 아니다.

검증: `Completer`로 파일 복사 또는 ingest를 지연시키는 Fake를 주입한다. 저장 중
모든 조작, 반복 탭, 실패 후 재시도, 성공 후 원본·DB 개수 및 중복 기록 부재를 확인한다.
실제 시간 지연이나 실제 플러그인에 의존하지 않는다.

### BF-02: 라벨에 따른 비교 기준

**코드상 기준 불일치 확인.**

- `lib/features/records/records_timeline_logic.dart`: 전체 타임라인과
  `findCompareTarget`은 `normalizeLabel`로 같은 라벨끼리 계산한다. 반면
  `collectByDirection`은 인접 행끼리 경과일을 계산하며 호출자가 대상을 좁힌다는
  주석이 있다. 실제 `records_screen.dart`는 라벨 필터 없이 전체 entries를 넘긴다.
- `lib/features/compare/compare_dates_screen.dart`: `_applyDefaults`는 라벨과
  공통 방향을 확인하지 않고 최신 두 기록을 자동 선택한다.
- `lib/features/capture/providers/capture_providers.dart`: 이전 사진 가이드는
  방향별 최신 파일을 선택하며 본인/다른 라벨을 구분하지 않는다. 라벨 입력은 리뷰에 있다.

계약: 방향 모아보기의 기간도 같은 라벨의 이전 사진을 기준으로 계산한다. 자동 날짜
선택은 본인 기록 중 공통 방향이 있는 쌍을 우선한다. 쌍이 없을 때 다른 사람의 기록을
조용히 채우지 말고 수동 선택을 안내한다. 촬영 기본 가이드는 본인 사진을 사용한다.
수동 비교는 자유 라벨을 유지하며 서로 다른 라벨을 골랐다는 사실을 표시한다.
회원·프로필·대상 테이블이나 새 사용자 개념을 만들지 않는다.

검증: 본인→다른 라벨→본인의 날짜 순서, 공백 라벨, 같은 날 여러 촬영, 공통 방향
부재, 본인 사진 파일 유실 시 같은 라벨의 과거 사진으로 대체, 자동 선택 후보 부재.
타임라인 화면과 비교 흐름 모두 검증한다.

### BF-03: 비교 기간 계산

**이번 UI 변경에 남은 계산 방식 불일치.**

`compare_dates_screen.dart`는 지역 시간 자정을 직접 `difference(...).inDays.abs()`로
계산한다. 기존 `records_timeline_logic.dart`의 `daysBetween`은 UTC 날짜로 변환해
서머타임 경계에서도 달력 일수를 보존한다. 새 화면도 기존 함수를 사용하거나 날짜
계산을 core의 작은 순수 함수로 옮겨 공통화한다. UI에 장문의 날짜 계산식을 남기지 않는다.

검증: 같은 날 0일, 7일, 이전/이후 교환 후 같은 기간, 연·월 경계, 시각 포함 입력,
서머타임 경계. 테스트 실행 기기의 시간대에 따라 성공 여부가 달라지면 안 된다.

### BF-04: 설정 저장 실패 및 저장 순서

**코드상 실패 상태와 순서 보장 부족 확인, 실제 실패는 Fake로 재현 필요.**

- `GridSettingsController.update`는 UI 값을 먼저 바꾸고 `_service.save`를 await하지만
  실패를 상태로 전환하지 않는다. 슬라이더 변경마다 저장 호출이 발생한다.
- `AppSettingsController.updateSettings`는 저장 후 상태를 바꾸지만 실패를 사용자에게
  알리는 상태가 없다. `SettingsScreen`은 이 Future를 `unawaited`로 호출한다.
  빠르게 서로 다른 설정을 변경하면 완료 순서와 이전 값 사용 문제가 생길 수 있다.
- `grid_settings_service.dart`와 `app_settings_service.dart`의 `setString`/`remove`
  결과는 확인하지 않는다. 해당 API의 실패 계약도 구현 단계에서 확인한다.

계약: 진행·실패·재시도를 구분하고 마지막 선택 의도를 보존한다. 저장 큐 또는 최신
요청 병합을 이용해 오래된 저장 완료가 최신 선택을 덮어쓰지 않게 한다. 슬라이더는
실시간 미리보기를 유지하되 영속 저장을 적절히 합친다. 격자 변경만으로 카메라 전체가
오류 화면으로 전환되지 않게 하고, 저장 실패 상태는 별도로 표시할 수 있어야 한다.

검증: 역순 완료하는 Fake, 저장 예외, 여러 필드 연속 변경, 재시도, 저장 실패 후
현재 UI 값과 재시작 값. provider/controller 테스트와 화면 테스트를 함께 추가한다.

### BF-05: 여러 사진 중 비교 사진 선택

**현재 기능 제한 확인, 후속 제품 개선 후보.**

`compare_logic.dart`의 `photoForDirection`은 첫 사진만 반환하고 타임라인·방향
모아보기도 첫 장을 대표로 쓴다. 갤러리 등록은 같은 날·같은 방향 여러 장을 허용한다.
따라서 사용자가 비교하려는 컷을 직접 고를 수 없는 경우가 있다. 기존 기록에 여러
사진을 보관하는 계약을 유지하고 비교 직전 선택을 추가하는 방향이 적절하다.

계약: 선택된 사진 id를 비교·내보내기까지 전달하고, 선택 사진이 삭제되면 복구 선택을
안내한다. 대표 사진 선정은 생성 시각·id 등 안정적인 정렬로 정의한다. 최초 단계에서는
대표 사진 필드를 DB에 추가하지 않아도 되는 구현을 우선 검토한다.

### BF-06: 검색과 장기 사용 성능

**미구현 경험 및 성능 위험 후보, 계측 전 병목으로 단정하지 않는다.**

현재 타임라인은 기록·사진 메타데이터 전체를 조회하며 `buildTimelineRows`는 같은 라벨의
이전 기록을 행마다 다시 찾는다. 날짜·기간·메모 검색은 없다. 실제 사진을 무작정 수천 장
만들지 말고 대량 Fake 메타데이터로 조회·필터·정렬을 계측한다. 확인된 병목부터 최적화한다.
페이지 조회를 도입하면 페이지 경계의 월 헤더·같은 날 회차·이전 기록 비교가 깨지지 않게 한다.
검색 라벨은 자유 문자열 필터이며 사용자/프로필 기능으로 확장하지 않는다.

### BF-07: 저장 공간의 신뢰성과 파일 정리

**통계의 표시 한계와 삭제 후 잔여 파일 가능성 확인.**

`StorageStatsServiceImpl.collect`는 실제 파일이 없으면 0바이트지만 사진 개수에는
포함한다. 파일 I/O를 서비스 내부에서 직접 수행하므로 존재·크기 검사도 대체 가능한
경계가 필요하다. 사진/기록 repository의 파일 삭제 실패는 best effort로 로그만 남는다.
통계는 DB 참조 파일만 집계하므로 남은 미참조 파일 용량을 놓칠 수 있다.

먼저 정상 파일·누락 파일을 구분해 표시하고 실패/재시도를 제공한다. 정리가 필요하면
삭제 실패 재시도 등 최소 경로를 검토한다. DB에 참조된 원본, staging/처리 중 파일,
경로 범위를 검증 없이 삭제하는 자동 스캔은 금지한다. 데이터 유실 위험이 있는 별도
정리 동작은 사용자 확인과 서비스·리포지토리 경계를 유지한다.

### BF-08: 전체 화면·사진 구도 검증 확장

**현재 자동 검증 범위의 공백과 문서 오류 확인.**

`test/design/responsive_ui_test.dart`는 날짜·방향 선택, 빈 기록, 기록 사진과 촬영
진행 표시를 다룬다. 카메라 전체, 키보드가 열린 등록·리뷰, 상세·원본·비교·내보내기·
저장 공간 전체의 확대 글꼴 검증까지 완료한 것은 아니다. `compare_view_screen.dart`의
고정 레이아웃 및 슬라이더/하단 컨트롤은 작은 가로 화면에서 특히 확인한다.

가로·세로·정사각·EXIF 회전 사진을 이용해 원본 비율, 격자 좌표, 확대/이동 동작,
비교 미리보기와 생성 이미지의 구도를 검증한다. 구도 불일치는 재현 후 수정하며,
원본 파일을 크롭·보정하지 않는다. 단계 3/3 안내와 설정·내보내기 상태의 접근성도 점검한다.

`docs/device-smoke-checklist.md`의 “같은 날 다시 촬영하면 기존 기록에 추가” 항목은
현재 구현 및 테스트의 “촬영 한 번마다 새 기록”과 충돌한다. 코드를 문서에 맞춰
기록 합치기로 되돌리지 말고 체크리스트를 현 계약으로 고친다.

## 작업 경계와 전달 결과

`AGENTS.md`가 최우선이다. 로그인/서버/클라우드/백업·복원/잠금/PIN/생체 인증/
암호화/워터마크/회원·프로필을 추가하지 않는다. Android 백업·D2D와 iOS 컨테이너
기본값, 상대경로 저장, 원본 보존, 명시적 삭제 확인을 유지한다.

플랫폼 I/O는 provider가 노출하는 인터페이스로 주입하고, 주요 상태·조작에는 기존
규칙의 Semantics.identifier와 ValueKey를 함께 둔다. DB 스키마 변경이 실제 필요하면
schemaVersion과 누적 마이그레이션을 같이 추가한다. 플랫폼 프로젝트를 재생성하지 않는다.

구현 후 수정 Dart 파일만 format하고 `flutter analyze`, `flutter test`를 실행한다.
플러그인 변경 및 카메라·저장·공유 동작은 Android/iOS에서 확인하고, 장비가 없으면
미검증 조합을 `ROADMAP.md`에 남긴다. 실기기 확인을 위젯 테스트로 대체했다고 쓰지 않는다.
